# 해시 · HMAC · 전자서명 (Hash · HMAC · Digital Signature)

메시지에 붙여 보내는 세 가지 값이 각각 무엇을 막고 무엇을 못 막는지를, 같은 메시지를 바꿔치기하는 공격으로 비교한다. 해시(SHA-256)는 비밀이 없어 누구나 다시 계산할 수 있고, HMAC(HMAC-SHA256)은 키를 가진 쪽만, 전자서명(Ed25519)은 개인키를 가진 쪽만 유효한 값을 만든다. 공격은 `amount=5000` 메시지를 `amount=9000`으로 바꾸는 것 하나다. 세 방식에 같은 공격을 보내 결과가 갈리는 것을 한 실행에서 본다.

글: [해시, HMAC, 전자서명 — 무결성과 출처 증명 구분](https://sgom.github.io/posts/hash-hmac-signature/)

## 무엇을 보이나

받는 쪽의 검증은 방식마다 함수 하나다(`verifyHash`, `verifyHmac`, `verifySignature`). 받은 메시지와 받은 값을 넣으면 통과 여부가 나온다. 방식마다 세 줄이 같은 순서로 나온다. 원본, 메시지만 바꾼 것, 공격자가 값까지 다시 만든 것이다.

1. **해시(SHA-256):** 메시지만 바꾸면 검증에 실패한다(우연한 손상은 잡힌다). 그러나 공격자가 바꾼 메시지의 해시를 다시 계산해 함께 보내면 통과한다. 계산에 비밀이 없어서다. 무결성만 주고 출처는 보장하지 못한다.
2. **HMAC(HMAC-SHA256):** 키를 모르는 공격자는 바꾼 메시지에 맞는 태그를 만들지 못해 검증이 실패한다. 키를 공유한 쌍방 사이의 출처+무결성. 다만 검증자도 같은 키를 가져 같은 태그를 만들 수 있으므로(마지막 두 줄이 동일) 제3자에게 누가 만들었는지 증명하지 못한다. 부인 방지는 없다.
3. **전자서명(Ed25519):** 개인키 없는 공격자는 서명을 위조하지 못한다. 공격자가 자기 키쌍으로 서명해도 검증자는 원래 서명자의 공개키로 검증하므로 실패한다. 공개키로 누구나 검증할 수 있어 공개 검증 가능한 출처 증명이 된다.

## 실행

```
node hmac-signature/integrity.mjs
```

Node.js 24 표준 라이브러리(`node:crypto`)만 쓴다. 외부 라이브러리·네트워크 없음. (확인에 쓴 버전 v24.15.0)

## 실행 출력

```
== 1. 해시
SHA-256(amount=5000) = 75064a859c7451720592b01db2ac8810115ae9773b1477fd93c68b1891d2c0fe
원본 메시지 + 원본 해시            -> 통과 true
바꾼 메시지 + 원본 해시            -> 통과 false
바꾼 메시지 + 공격자가 계산한 해시 -> 통과 true

== 2. HMAC
HMAC(amount=5000) = 96fe6de71f074337876b97b42f5c9b23f5a5af637b1f4d2d2ee5f17b92a24df7
원본 메시지 + 원본 태그                 -> 통과 true
바꾼 메시지 + 원본 태그                 -> 통과 false
바꾼 메시지 + 추측한 키로 만든 태그     -> 통과 false
보낸 쪽이 만든 태그   908f8edfa313592486afba6caa21e0d76faa136db2fbcf497015b07f95aec8d5
검증자가 만든 태그    908f8edfa313592486afba6caa21e0d76faa136db2fbcf497015b07f95aec8d5

== 3. 전자서명
서명 키쌍은 실행마다 새로 생성(서명 값은 매번 달라 찍지 않는다)
서명 길이 64바이트
원본 메시지 + 서명                     -> 통과 true
바꾼 메시지 + 서명                     -> 통과 false
바꾼 메시지 + 공격자 키로 만든 서명    -> 통과 false
```

- **1번 셋째 줄만 `true`다.** 해시는 공격자가 다시 계산한 값이 통과한다(보호 안 됨). HMAC과 전자서명은 공격자가 다시 만든 값이 거부된다.
- **HMAC 마지막 두 줄은 `908f8edf…`로 같다.** 검증자도 같은 키를 가져 보낸 쪽과 똑같은 태그를 만든다. 전자서명에는 이에 대응하는 줄이 없다. 검증자가 가진 것은 공개키뿐이고, 공개키로는 서명을 만들 수 없다.

해시와 HMAC 값은 실행마다 같다. HMAC 키는 출력을 고정하려고 문자열(`shared-secret-key`)을 썼다. 실제 키는 해시 출력 길이 이상의 무작위 바이트로 만든다([RFC 2104 3절](https://www.rfc-editor.org/rfc/rfc2104.html#section-3)). 전자서명 키쌍은 실행마다 새로 만들어 서명 값이 매번 다르므로, 서명 값 대신 길이(64바이트)와 검증 결과만 찍는다.

값 비교는 `crypto.timingSafeEqual`로 한다(블로그 예시의 `MessageDigest.isEqual`에 대응). 상수 시간 비교가 실제로 필요한 자리는 **HMAC뿐**이다. 비교 시간이 내용에 따라 달라지면 공격자가 그 차이로 유효한 태그를 앞에서부터 한 바이트씩 맞춰 갈 수 있기 때문이다. 해시는 비밀이 없고 공격자가 값을 직접 계산할 수 있어 비교 시간이 새도 얻을 것이 없고, 전자서명 검증은 공개키·메시지·서명이 모두 공개라 비교로 샐 비밀 자체가 없다. 상수 시간 비교의 원리는 [`timing-attack/`](../timing-attack) PoC가 따로 다룬다.

## 한계

- **세 원시 함수의 보장 차이만 보인다.** 키 관리, 키 교환, 공개키 진위 확인(인증서·핑거프린트), 재전송 방지(nonce·타임스탬프)의 현실적 어려움은 다루지 않는다. 이것들은 각각 별도 문제다.
- **공격은 "메시지 변조 후 값 재생성" 하나다.** HMAC에서 추측한 키로 만든 태그가 거부되는 것은 추측 한 번의 실패이지 위조 불가능성의 증명이 아니다. 전자서명에서는 공격자가 자기 키로 서명해도 검증자가 원래 서명자의 공개키로 검증하므로 실패한다. 키 없이 태그·서명을 만들 수 없다는 근거는 [RFC 2104 6절](https://www.rfc-editor.org/rfc/rfc2104.html#section-6)과 [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html)의 보안 논의에 있다.
