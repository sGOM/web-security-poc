# IDOR (Insecure Direct Object Reference, 접근 제어 누락)

서버가 "로그인했는가"는 확인하지만 "이 리소스가 그 사용자 것인가"(소유자 확인)를 확인하지 않으면, 로그인한 사용자가 요청의 리소스 ID만 바꿔 남의 리소스를 꺼낸다. 주문·영수증·프로필처럼 ID로 직접 가리키는 리소스가 표적이 된다. 순차 ID면 남의 ID를 추측하기도 쉽다.

글: [IDOR — 로그인은 확인하고 소유자는 확인하지 않을 때](https://sgom.github.io/posts/idor/)

## 무엇을 보이나

주문 3건을 인메모리에 둔다. order 1·2는 alice, order 3은 bob 소유다. 각 주문에 `ownerId`와 민감한 내용(카드 끝자리, 주소)이 있다. 세션은 `Authorization: Bearer <토큰>`으로 흉내 낸다(`sess-alice` → alice).

- `/vuln/order?id=`: 로그인만 확인하고 ID로 바로 주문을 꺼내 준다 (취약)
- `/safe/order?id=`: 로그인 + 그 주문의 `ownerId`가 현재 세션 사용자와 같은지 확인한다. 아니면 404 (고침)

두 경로 모두 비로그인은 401이다. 차이는 로그인 **이후** 소유자를 보느냐뿐이다. alice 세션으로 자기 주문(1)과 남의 주문(3)을 양쪽에 보내 결과가 갈리는 것을 한 실행에서 대조하고, id=1..3을 훑어 어디까지 보이는지도 보인다.

## 실행

Node.js 24. 의존성 없음. 서버는 `127.0.0.1`에만 뜬다.

```sh
node idor.mjs
```

## 읽는 법

- **비로그인**: 토큰이 없으면 두 경로 모두 401이다. 취약한 쪽도 "로그인했는가"는 본다. 차이는 로그인 이후 소유자를 보느냐뿐이다. 이 줄이 있어야 뒤의 결과가 "인증이 없는 엔드포인트"가 아니라 IDOR임이 드러난다.
- **자기 주문 (id=1)**: 양쪽 다 200으로 alice의 주문을 내려준다. 고친 쪽이 멀쩡한 요청까지 막지는 않는다.
- **남의 주문 (id=3)**: 공격과 방어가 갈리는 지점이다. 취약한 쪽은 로그인만 봤으니 bob의 카드 끝자리·주소를 그대로 내려준다(200). 고친 쪽은 `order.ownerId !== user`라서 404로 막는다. alice는 세션을 바꾸지도, 권한을 올리지도 않았다. `id=1`을 `id=3`으로 바꿨을 뿐이다.
- **순차 ID 열거**: ID가 1, 2, 3으로 이어지니 남의 것을 추측하기 쉽다. 취약한 쪽에서는 셋 다 200이라 alice가 bob 주문까지 전부 긁는다. 고친 쪽은 자기 것(1·2)만 200, 남의 것(3)은 404다.

## 소유자 확인 (고친 쪽 핵심)

```js
if (url.pathname === "/safe/order") {
  // 고침: 로그인 + 그 주문의 ownerId가 현재 세션 사용자와 같은지 확인한다.
  const order = orders[id];
  // 존재하지 않거나 남의 주문이면 똑같이 404로 응답해 존재 여부를 숨긴다.
  if (!order || order.ownerId !== user) {
    reply(404, { error: "not found" });
    return;
  }
  reply(200, { id: Number(id), ...order });
  return;
}
```

핵심은 `order.ownerId !== user` 한 줄이다. 로그인 확인(`user`)과 소유자 확인(`ownerId === user`)은 별개다. 취약한 쪽은 앞만 했다. 없는 주문과 남의 주문을 **같은 404**로 응답하는 것도 의도다. 403("권한 없음")으로 답하면 "그 ID의 주문은 존재한다"는 사실이 새어, 공격자가 유효한 ID를 열거하는 단서가 된다. 404로 통일하면 존재 여부 자체를 숨긴다.

## 한계

- **인가 모델이 단순하다.** 여기서는 소유자 본인만 접근한다. 실무에는 관리자·협업자·조직 공유처럼 "소유자는 아니지만 봐도 되는" 경우가 있다. 그때는 `ownerId === user` 대신 정책 함수(`can(user, "read", order)`)로 확장한다. 이 PoC는 그 확장을 재현하지 않는다.
- **404로 숨기는 것이 늘 정답은 아니다.** 공유 링크처럼 존재를 알려도 되는 리소스나, 사용자에게 "권한이 없다"고 명확히 알려야 하는 UX에서는 403이 맞다. 정보 노출과 사용성 사이의 선택이며, 이 PoC는 "존재를 숨기는" 한쪽만 보인다.
- **세션은 토큰 맵으로 흉내 냈다.** 실제 로그인·세션 만료·토큰 위조 방어는 범위 밖이다. IDOR은 인증이 멀쩡해도(토큰이 진짜 alice여도) 인가에서 터지는 문제임을 보이는 데 집중했다.
- **ID 추측 난이도는 별개 방어다.** 순차 정수 대신 UUID를 쓰면 열거는 어려워지지만, 그것은 완화책일 뿐 접근 제어의 대체가 아니다. UUID를 알아낸 요청에는 여전히 소유자 확인이 필요하다. 이 PoC는 순차 ID만 다룬다.
