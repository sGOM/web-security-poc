# SSRF (Server-Side Request Forgery)

사용자가 준 URL을 서버가 대신 요청하는 기능이 있으면, 공격자는 그 URL에 내부 주소를 넣어 외부에서 닿을 수 없는 자원을 서버가 대신 읽게 만든다. 클라우드 메타데이터 주소(169.254.169.254)나 내부 관리 API가 표적이 된다.

글: [SSRF — 서버가 대신 요청할 때 내부 주소에 닿는 것](https://sgom.github.io/posts/ssrf-basics/)

## 무엇을 보이나

프록시 서버 하나가 `?url=`로 받은 주소를 대신 가져온다. 같은 호스트에 내부 전용 메타데이터 서버를 띄워 표적으로 쓴다.

- `/vuln/fetch`: 검사 없이 가져온다 (취약)
- `/safe/check`: 호스트 이름을 실제 IP로 풀어 사설 대역이면 거절한다

수정본은 `check`로 분류만 보인다. 실제 외부 요청을 보내지 않으려고, 가져오기 단계와 분리해 "허용/차단" 판정만 출력한다.

## 실행

Node.js 24. 의존성 없음. 모든 서버는 `127.0.0.1`에만 뜬다.

```sh
node ssrf.mjs
```

```
$ node ssrf.mjs
Node.js v24.15.0
내부 메타데이터 서버: 127.0.0.1:59794 (외부에 열려선 안 됨)

== 1. 취약한 프록시로 내부 서버를 가져온다
  대상: http://127.0.0.1:59794/secret
  취약 -> 200 {"status":200,"body":"{\"secret\":\"INTERNAL-API-KEY-abc123\",\"path\":\"/secret\"}"}

== 2. 수정본은 가져오기 전에 IP를 분류한다 (요청을 보내지 않는 /safe/check)
  http://93.184.216.34/
    -> 허용 (resolved 93.184.216.34)
  http://127.0.0.1:59794/secret
    -> 차단 (사설 IP 차단 127.0.0.1 -> 127.0.0.1)
  http://169.254.169.254/latest/meta-data/
    -> 차단 (사설 IP 차단 169.254.169.254 -> 169.254.169.254)
  http://10.0.0.5/
    -> 차단 (사설 IP 차단 10.0.0.5 -> 10.0.0.5)
  file:///etc/passwd
    -> 차단 (허용하지 않는 스킴 file:)
```

포트 번호는 실행마다 달라진다.

## 읽는 법

- 1단계: 취약한 프록시가 내부 메타데이터 서버의 비밀(`INTERNAL-API-KEY-abc123`)을 가져왔다. 공격자는 프록시를 거쳐 외부에서 내부를 읽는다.
- 2단계: 수정본은 호스트를 IP로 푼 뒤 분류한다. 공개 IP(93.184.216.34)는 허용, 루프백·클라우드 메타데이터(169.254.169.254)·사설 대역(10.0.0.5)은 차단, `http`가 아닌 스킴(`file:`)도 차단이다.

## 한계

- 사설 IP 목록은 대표적인 것만 담았다. IPv6 대역, `0.0.0.0`의 다른 표기, 10진수·8진수로 쓴 IP 우회는 다루지 않는다.
- **DNS 리바인딩은 막지 못한다.** 검사할 때 푼 IP와 실제 가져올 때 푸는 IP가 다를 수 있다(TOCTOU). 검사 때 공개 IP를 주고 가져올 때 사설 IP로 바꾸는 공격이 있다. 실무에서는 푼 IP로 직접 연결하거나 리다이렉트를 따라갈 때 매번 다시 검사한다. 이 PoC는 그 경로를 재현하지 않는다.
- 공개 IP 93.184.216.34는 분류용 리터럴이고, 실제로 요청을 보내지는 않는다.
