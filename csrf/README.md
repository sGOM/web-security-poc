# CSRF (Cross-Site Request Forgery)

로그인한 사용자의 브라우저는 공격자 페이지가 만든 요청에도 세션 쿠키를 붙인다. 서버가 쿠키만 보고 요청을 믿으면, 사용자가 누르지 않은 이체가 실행된다.

글: [CSRF — 쿠키가 자동으로 실리는 것이 왜 문제인가](https://sgom.github.io/posts/csrf-basics/)

## 무엇을 보이나

서버 하나에 이체 주소 셋을 둔다.

| 주소 | 서버가 확인하는 것 |
|---|---|
| `/transfer/none` | 세션 쿠키뿐 (취약) |
| `/transfer/token` | 세션 쿠키 + `X-CSRF-Token` 헤더가 세션의 토큰과 같은가 |
| `/transfer/origin` | 세션 쿠키 + `Origin` 헤더가 서버 자신의 출처인가 |

각 주소에 요청을 둘씩 보낸다.

- **은행 페이지에서 나간 요청**: 쿠키, 자기 출처의 `Origin`, 토큰이 모두 실린다.
- **공격자 페이지에서 나간 요청**: 쿠키는 브라우저가 붙여 준다. `Origin`은 공격자의 것이고 토큰은 모른다.

## 실행

Node.js 24. 의존성 없음.

```sh
node csrf.mjs
```

```
Node.js v24.15.0

/transfer/none
  은행 페이지   -> 200 이체 완료, 잔액 9000
  공격자 페이지 -> 200 이체 완료, 잔액 8000

/transfer/token
  은행 페이지   -> 200 이체 완료, 잔액 7000
  공격자 페이지 -> 403 CSRF 토큰 불일치

/transfer/origin
  은행 페이지   -> 200 이체 완료, 잔액 6000
  공격자 페이지 -> 403 허용하지 않는 출처 https://evil.example
```

## 읽는 법

- `/transfer/none`은 공격자 쪽 요청도 200이고 잔액이 줄었다. 서버에게 두 요청은 같은 사용자의 요청이다.
- `/transfer/token`과 `/transfer/origin`은 공격자 쪽 요청에 403을 낸다. 잔액은 은행 페이지의 요청만큼만 줄었다.

## 한계

브라우저를 쓰지 않는다. HTTP 클라이언트로 두 요청의 헤더를 직접 만들어, 서버가 두 모양의 요청을 어떻게 가르는지를 본다. 브라우저가 실제로 그렇게 보내는지는 이 PoC가 보이지 않는다. 쿠키가 다른 사이트에서 시작된 요청에 실리는지는 `SameSite` 속성과 브라우저에 달려 있다.

## 파일

- `csrf.mjs`: 서버와 두 종류의 요청을 한 파일에 담았다. 서버는 임의의 로컬 포트에 뜨고 실행이 끝나면 닫힌다.
