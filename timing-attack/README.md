# 타이밍 공격 (Timing Attack)

비밀 값(토큰·비밀번호 해시·API 키)을 "앞에서부터 바이트별로 비교하다 처음 틀린 곳에서 바로 멈추는" 비교로 검사하면, 비교에 걸리는 시간이 "앞에서 몇 바이트가 맞았는지"에 비례해 늘어난다. 맞은 접두가 길수록 느리다. 공격자는 이 시간 차이를 측정해 비밀 값을 앞에서부터 한 바이트씩 알아낼 수 있다. 방어는 입력이 무엇이든 같은 시간이 걸리는 상수 시간 비교(`crypto.timingSafeEqual`)다.

글: [타이밍 공격 — 비밀 값 비교에 걸리는 시간이 새는 정보](https://sgom.github.io/posts/timing-attack/)

## 무엇을 보이나

16바이트 토큰을 hex로 표현한 32자 비밀 하나를 두고, 두 비교 함수를 나란히 둔다.

- `vulnEqual`: 바이트별로 비교하다 처음 틀린 곳에서 바로 `return false` 한다(조기 반환, 취약).
- `safeEqual`: `crypto.timingSafeEqual(Buffer, Buffer)`로 끝까지 본다(상수 시간, 고침).

데모는 두 가지다. 네트워크를 쓰지 않는다. 로컬 함수의 실행 시간을 `process.hrtime.bigint()`로 직접 잴 뿐이고, 외부로 나가는 요청은 없다.

1. **데모 1 (추세):** 비밀과 앞에서 0·8·16·24·32자가 일치하는 후보를 각각 많이 반복 비교해 1회당 평균 시간을 잰다. 취약한 쪽은 일치 자 수에 비례해 시간이 늘고, 상수 시간 쪽은 평평하다.
2. **데모 2 (복원):** 타이밍만으로 비밀을 복원한다. 각 자리에서 16개 hex 후보를 재고 가장 느린 것을 그 자리의 정답으로 택하는 과정을 32자리에 반복한다. 취약한 쪽은 비밀을 그대로 복원하고, 상수 시간 쪽은 아무 관계 없는 값이 나온다.

### 취약: 조기 반환 비교

```js
function vulnEqual(input, secret) {
  if (input.length !== secret.length) return false;
  for (let i = 0; i < secret.length; i++) {
    if (input.charCodeAt(i) !== secret.charCodeAt(i)) return false; // 틀리면 즉시 멈춘다
    let acc = i;
    for (let k = 0; k < 40; k++) acc = (acc * 1103515245 + 12345) & 0x7fffffff;
    SINK += acc;
  }
  return true;
}
```

JS `===`나 `Buffer.equals`는 엔진 최적화로 타이밍이 흐려질 수 있어, 직접 바이트 루프를 돌며 불일치 시 바로 멈춘다. 일치한 바이트마다 하는 고정된 작은 작업(`k` 루프)은 신호 증폭용이다. 실제 `memcmp`도 바이트마다 일정한 일을 하지만 그 시간이 타이머 해상도보다 작아 가려지므로, 같은 성질(일치 바이트 수에 비례하는 시간)을 측정 가능한 크기로 키웠다. 신호의 원리는 바꾸지 않았다. `acc`를 바깥 변수 `SINK`에 누적해 엔진이 루프를 통째로 지우지 못하게 막는다.

### 고침: 상수 시간 비교

```js
function safeEqual(input, secret) {
  const a = Buffer.from(input);
  const b = Buffer.from(secret);
  if (a.length !== b.length) return false;
  return crypto.timingSafeEqual(a, b);
}
```

[`crypto.timingSafeEqual`](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptotimingsafeequala-b)은 두 버퍼의 모든 바이트를 끝까지 보며, 일치 여부와 무관하게 같은 시간이 걸린다. 길이가 다르면 예외를 던지므로 길이를 먼저 확인한다. 다만 길이 분기 자체가 "길이가 맞았는지"라는 정보를 흘릴 수 있어, 길이 오라클까지 없애려면 양쪽을 고정 길이 해시로 바꿔 항상 같은 길이로 비교한다.

```js
function safeEqualHashed(input, secret) {
  const a = crypto.createHash('sha256').update(input).digest();
  const b = crypto.createHash('sha256').update(secret).digest();
  return crypto.timingSafeEqual(a, b);
}
```

## 노이즈를 어떻게 다루나

타이밍은 노이즈가 크다. 측정값은 다음으로 다룬다.

- **`process.hrtime.bigint()`로 잰다.** 나노초 단위 단조 증가 시계다. 한 번의 호출은 너무 짧아 노이즈에 묻히므로, `REPS`회 반복한 총 시간을 `REPS`로 나눠 1회당 평균(ns/op)을 구한다.
- **워밍업 라운드를 버린다.** 앞 3라운드는 JIT 워밍업용으로 버리고 나머지만 집계한다.
- **라운드별 평균의 중앙값을 쓴다.** 측정을 여러 라운드로 나누고 라운드별 평균의 중앙값을 취해, GC나 순간 부하로 튄 값을 걸러낸다.
- **복원(데모 2)은 후보를 번갈아 잰다(인터리브).** 한 자리에서 16개 후보를 잴 때, 한 후보를 연속으로 다 재고 넘어가면 CPU 주파수 변화 같은 느린 드리프트가 특정 후보에만 실려 엉뚱한 자를 고르게 된다. 라운드마다 16개를 번갈아 재면 드리프트가 모든 후보에 고르게 실려 상쇄된다. 이 한 가지가 깊은 자리(뒤쪽 바이트)의 복원 성공을 좌우했다(아래 「한계」 참고).

**수치의 절대값이 아니라 추세를 본다.** ns/op 값은 실행마다, 기계마다 다르다. 보는 것은 "취약한 쪽에서 접두 일치가 늘 때 시간이 단조 증가하는가"와 "상수 시간 쪽이 접두 길이와 무관하게 평평한가"다.

## 실행

Node.js 24. 의존성 없음. 네트워크를 쓰지 않는다.

```sh
node timing-attack.mjs
```

측정량이 많아 한 번 실행에 몇 분 걸린다. 반복 횟수는 환경 변수로 조절한다: `REPS`/`ROUNDS`(데모 1), `REC_REPS`/`REC_ROUNDS`(데모 2). 기본값은 `REPS=50000 ROUNDS=11 REC_REPS=8000 REC_ROUNDS=21`.

## 실제 출력

아래는 `timing-attack.mjs`를 실행한 대표 출력이다. ns/op 수치는 실행마다 달라진다.

```

[데모 1] 접두 일치 바이트 수별 1회 비교 평균 시간 (ns/op)
         REPS=50000 ROUNDS=11 (워밍업 3라운드 제외), 라운드별 평균의 중앙값

  일치자수 | 취약 vulnEqual | 상수 safeEqual
  ---------+----------------+----------------
       0   |          4.9   |        295.7
       8   |       1824.7   |        277.7

  취약: 일치 자 수에 비례해 시간이 는다 → 접두 일치 길이가 샌다.

         REC_REPS=8000 REC_ROUNDS=21
```

## 읽는 법

- **데모 1 취약 열:** `4.9 → 1824.7 → 3569.1 → 5384.8 → 7096.1`. 일치 자가 8자 늘 때마다 약 1800ns씩 거의 일정하게 는다. 접두 일치 수가 그대로 시간에 새어 나온다. 0자 일치는 첫 자부터 틀려 바로 멈추므로 함수 호출 비용(≈5ns)만 든다.
- **데모 1 상수 열:** `295.7 → 277.7 → 263.4 → 254.6 → 260.0`. 좁은 구간(약 40ns 폭)에서 오르내릴 뿐 접두 일치 수와 단조 관계가 없다. 32자 전부 일치(`260.0`)가 0자 일치(`295.7`)보다 오히려 작아, 남은 변동이 신호가 아니라 노이즈임을 보여준다.
- **데모 2:** 취약한 비교에서는 각 자리의 정답 후보만 한 바이트 더 일치해 한 단위만큼 느리다. 그 "가장 느린 후보"를 자리마다 골라 이어 붙이면 비밀이 그대로 복원된다. 상수 시간 비교에서는 어느 후보도 더 느리지 않아 고른 값이 무작위에 가깝고, 비밀과 일치하지 않는다.

측정값의 안정성은 여러 번 돌려 확인했다. 데모 1의 취약 열 단조 증가·상수 열 평탄은 매 실행 나왔다. 데모 2의 복원은 인터리브 측정으로 관측한 모든 실행(5회)에서 32자 전부를 복원했다. 인터리브 없이 후보를 연속으로 재던 초기 구현은 같은 반복 횟수에서 4회 중 2회만 전부 복원하고, 깊은 자리(28번째)나 드리프트가 낀 얕은 자리(7번째)에서 틀렸다.

## 한계

- **이 PoC는 로컬 함수 수준의 타이밍 차이만 보인다.** 네트워크 너머 원격 타이밍 공격의 실현 가능성은 다루지 않는다. 원격에서는 왕복 지연의 지터가 함수 수준 신호(여기서는 바이트당 ≈225ns)보다 훨씬 커서, 신호를 뽑아내려면 훨씬 많은 표본과 통계적 판별이 필요하다. 그 난이도는 이 PoC가 측정하지 않는다.
- **취약 함수의 신호는 증폭된 것이다.** 일치 바이트마다 한 고정 작업은 실제 `memcmp`의 바이트당 비용을 측정 가능한 크기로 키운 것이다. 조기 반환 비교가 "일치 접두 길이에 비례해 느려진다"는 성질 자체는 실제와 같지만, 증폭을 뺀 날것의 바이트별 비교에서 같은 추세를 이 PoC의 반복 횟수로 안정되게 뽑을 수 있는지는 확인하지 않았다.
- **복원(데모 2)은 확률적이다.** 관측한 5회 실행에서 모두 성공했으나 100% 보장은 아니다. 더 조용한 기계일수록, `REC_REPS`·`REC_ROUNDS`를 키울수록 안정된다. 더 시끄러운 기계에서 뒤쪽 바이트를 놓치면 그 두 값을 키운다. 한 자리라도 틀리면 그 뒤로는 접두가 어긋나 신호가 사라지므로 이후 자리는 무작위가 된다.
- **엔진 최적화에 기댄 부분이 있다.** `SINK` 누적으로 루프 제거를 막았지만, V8 버전이 바뀌면 최적화 양상이 달라져 데모 1의 절대 수치나 `vulnEqual`의 바이트당 비용이 달라질 수 있다. 확인한 것은 Node.js v24.15.0(V8) 한 버전이다.
- **상수 시간 열의 평탄은 "접두 길이와 무관"까지만 보인다.** `crypto.timingSafeEqual`이 모든 입력에 완벽히 동일한 시간을 쓴다는 증명은 아니다. 남은 미세 변동(약 40ns 폭)이 접두 일치와 단조 관계가 없다는 것만 측정했다.
- 후보들의 길이를 비밀과 같은 32자로 맞춰, `vulnEqual`의 길이 분기와 `timingSafeEqual`의 길이 예외를 둘 다 피했다. 길이가 다를 때의 타이밍 차이(길이 오라클)는 측정하지 않는다. `safeEqualHashed`는 길이 분기 없이 비교함을 코드로 보일 뿐, 그 타이밍은 측정하지 않는다.

## 파일

- `timing-attack.mjs`: 비밀, 두 비교 함수(`vulnEqual`/`safeEqual`)와 길이 오라클까지 없앤 변형(`safeEqualHashed`), 측정 도구, 데모 1(추세)과 데모 2(복원)를 한 파일에 담았다.
